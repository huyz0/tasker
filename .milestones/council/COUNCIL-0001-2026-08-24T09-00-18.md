# Next Work Recommendation

## What

Build the in-app notification surface for stalled-claim alerts: a notification
bell in the GUI shell, backed by per-user read/unread state, consuming the
`domain.task.stalled` events M25 already publishes — with the subscription,
badge and dismissal mechanism designed once, generically, so handoff and
review-request alerts can plug into it rather than each inventing its own alert
surface.

## Why

Every advisor except Product Roadmap scored this 4 or 5, and Product Roadmap's
dissent (2) rests on a bookkeeping argument rather than a substantive one — that
M21–M28 sit outside `roadmap.md`'s Phase 1/2 capability tables, which
`roadmap.md` itself explains is because those milestones were "sequenced by
explicit user priority." User Value (4) calls it a real improvement to the
workflow surface a Human User is actually on when triaging work, since M25 today
delivers the alert only by email; Dependency Order (4) is the reason it survives
the tie-break, naming two future consumers of the same pattern — handoff alerts
and review-request alerts — which makes it an enabler rather than a leaf, unlike
the candidate it displaced; Technical Debt (4) adds the inverse warning, that
building it narrowly for stalled claims alone re-creates the fragmentation it
should prevent. Implementation State (3) and Test Coverage (5) agree the hard
half is already done and proven: `apps/backend/src/lib/stalledClaimAlerts.ts:169`
publishes `domain.task.stalled`, M08's `consumers/auditProjector.ts` durably
projects it to `audit_log`, and the GUI's live-event path
(`apps/gui/src/hooks/useLiveEvents.ts`, `LiveStatusIndicator.tsx`) already ships
with tests — while no `Notification`-named component exists anywhere under
`apps/gui/src/features/`, confirming this is the deliberate hand-off M25's own
deferral note described ("deferred deliberately, so a future in-app notification
bell starts from a working data source"). Security (4) withholds the fifth point
for the one genuinely new thing here — per-user notification state is a new
isolation boundary — which is a scoping instruction, not an objection.

## How

Consume the existing pipeline rather than adding to it: `domain.task.stalled` is
already published to NATS by `lib/stalledClaimAlerts.ts` and already reaches
`audit_log` through M08's durable `consumers/auditProjector.ts`, so the bell
reads from the delivered projection and subscribes to live updates through
`EventService.SubscribeEvents` via the existing `useLiveEvents` hook — no new
subject, consumer or transport. The only net-new persistence is a per-user
read-state table; scope every query on it by `userId` and route it through
`lib/authz.ts`'s `assertOrgMember` primitive, because `modules/events/eventScope.ts`
already enforces exactly this org-membership-plus-per-agent-scope filter for the
same event class on the live feed, and an unscoped read here leaks one user's
alerts to another. Follow the two-dialect migration discipline
`db/schema.mysql.ts` and `db/schema.sqlite.ts` are hand-kept under, and model
the token/sweep hygiene on `lib/retentionSweep.ts` if read-state needs pruning.
On the GUI side, build the bell in `apps/gui/src/components/layout/` next to
`LiveStatusIndicator.tsx` — which is the closest existing precedent for a
live-updating shell affordance and ships with both a test and a story — and keep
the event-type-to-notification mapping in a table rather than a switch, so the
handoff and review-request alerts the M25 deferral names can register against it
without touching the bell.

## Field Compression — a caveat on the whole ranking

Ten of sixteen candidates finished within 0.52 weighted points of each other
(3.58 down to 3.07). `moderator.md` scopes the tie-break procedure to the top
two, which is what was applied above, but the compression is itself the most
important structural finding of this council and should temper how much
authority the ordinal ranking is given.

The cause is visible in the score matrix: no candidate scored 5 from both
0.20-weight advisors, and the candidates that *did* earn 5s clustered them in the
light lenses. Standards Documentation Truth Pass took 5 from Technical Debt,
Implementation State, Test Coverage, Security and Build & Deploy — and 1 from
both Product Roadmap and User Value, who correctly observed it is not a product
capability. Measured Concurrency took 5 from Dependency Order, Technical Debt and
Security, and 1 from User Value. The weighting scheme is doing precisely what it
was designed to do, but the consequence is that a genuinely excellent internal
task and a moderate user-facing one land on the same number by different routes.

Read the tiers, not the decimals:

- **Tier 1 — broad support across heavy and light lenses** (3.38–3.58):
  Notification Bell, CLI Ergonomics, Password Reset, Review-Queue Latency.
- **Tier 2 — excellent internal work, invisible to the product lenses**
  (3.07–3.25): Standards Truth Pass, Scope Vocabulary SSOT, Measured Concurrency,
  M08 Frontmatter Drift, Shared-Store Rate Limiting.
- **Tier 3 — contested or gated** (2.53–3.16): Deep-Link Completeness, CSP
  Headers, Graphical Editing, Signed Binaries, File-Size Debt.
- **Tier 4 — unanimous rejection** (1.00): CQRS.

A defensible alternative reading exists and should be named. `scoring-rubric.md`
phrases the tie band as applying to *any* two candidates within 0.5 rather than
only the top two. Under that broader reading, tiebreaker 1 sweeps the entire
compressed cluster, and the winner would be **Candidate 2, Measured Concurrency
at Declared Scale** — the only candidate that formally unblocks two *other
candidates on this very list* (ADR-0003's CQRS read-store deferral and the
rate-limiter store choice), a strictly stronger claim than the bell's "enables a
reusable pattern." This report follows `moderator.md`'s narrower top-two wording,
which is the operative procedure for Phase B. A human who prefers the broader
reading should take Measured Concurrency instead; the council's evidence supports

### The M08 fix is scoped wrong — M10 carries the same drift

Candidate 9 as proposed scopes the frontmatter repair to M08 alone. Three
advisors independently found the same species of defect in M10, and the moderator
verified both directly this session:

| Milestone | Frontmatter | Body |
| --- | --- | --- |
| M08 | `status: todo`, `exit_criteria_met: false`, `completed_at: null` | 17/17 tasks checked, **6/6 exit criteria checked**, `PROGRESS.md` says "Nothing" remains |
| M10 | `status: done`, `exit_criteria_met: true`, `completed_at: 2026-08-17` | **all 8 exit criteria unchecked** |

The two drift in opposite directions, which is why a single-file fix misses it:
M08 under-reports completed work, M10 over-reports it. M10 is the more dangerous
of the two — M08's frontmatter is conspicuously wrong and any reader notices,
whereas M10 asserts `exit_criteria_met: true` over a body that provides no
evidence for the claim, and nothing in the repository can tell whether those
eight criteria were met and left unticked or were never verified. Technical Debt
flagged this explicitly ("scoping the fix to M08 alone leaves the M10 instance of
the same defect live, meaning the fix is incomplete unless widened"), Dependency
Order flagged it as the candidate's scope-creep risk, and Implementation State
judged it "worth folding in at effectively no added cost."

Whenever Candidate 9 is scheduled, scope it as *all 22 milestone files*, not
M08 — and note that Build & Deploy verified `moon.yml`'s `doc-drift` task inputs
cover `README.md`, `architecture.md`, `mission.md`, `NAVIGATION.md` and
`STATE.md` but **not** per-milestone `MILESTONE.md` frontmatter, so nothing gates
this class of file today and nothing prevents the drift recurring the moment it
is fixed. A frontmatter-vs-body consistency check belongs in the same CI job as
`spec-drift` and `doc-drift`, and that gate is the durable half of the work.

### The sharpest lens disagreement: Password Reset, 5 from Test Coverage vs 2 from Security

Candidate 10 produced the widest defensible split in the council, and both
advisors are reasoning correctly from their own domain — this is not an error to
adjudicate, it is a real property of the work that the ranking's single number
hides.

- **Test Coverage scored 5** because the *test scaffolding* for this is
  effectively pre-built. M12's invite-email flow is an almost exact structural
  precedent for a reset-token email flow, and `mailer.test.ts`,
  `inviteEmail.test.ts`, `auth.test.ts`, `auth.handler.test.ts` and `authz.test.ts`
  already exist to extend. From this lens the work is "replicating the
  token-generation/expiry test pattern already proven for invites" — low effort,
  low regression risk.
- **Security scored 2** because a password reset is a *new authentication flow*,
  the highest-risk category it screens for. It needs a cryptographically
  unguessable single-use time-bound token, protection against user enumeration via
  response and timing differences, and its own rate limiting independent of
  `lib/loginRateLimiter.ts` to prevent reset-token brute-forcing — none of which
  exist. Broken password reset is an OWASP-class account-takeover vector.

Both are true simultaneously. The existence of good test scaffolding says nothing
about whether the *right* security properties get tested, and that is precisely
the gap: the invite-email precedent Test Coverage points to is a flow where the
recipient is *granted* access, not one where an attacker who guesses a token
*seizes* it. The precedent transfers mechanically and does not transfer
threat-model-wise.

The disagreement is also compounded by an interaction the council did not score:
Candidate 10 needs its own rate limiter, and Candidate 5 (Shared-Store
Distributed Rate Limiting) exists because the current one is per-instance and
multiplied by replica count. Building password reset on top of the in-process
limiter ships a brute-forceable reset endpoint into the `replicas: 2` topology
`deploy/kubernetes.yaml` already declares. If Candidate 10 is scheduled, either
sequence Candidate 5 first or scope the shared-store fix into it.

The practical resolution: if password reset is chosen, it is not the small item
its 3.44 and its test-precedent suggest. Budget a security review of the token
flow as an exit criterion, not a follow-up.

#### 14. Shared-Store Distributed Rate Limiting

- **Score**: 3
- **Rationale**: The interface is already clean (`lib/rateLimit.ts`, `lib/loginRateLimiter.ts`, a shared `RateLimitDecision` type) so the code change is contained, but the candidate's own description flags an **undecided infrastructure choice** — MySQL counters (zero new infra, since MySQL is already the clustered-deployment database) versus a new Redis-class dependency, which the single-binary/standalone story must keep strictly optional.
- **Evidence**: `architecture.md`'s NFR table: rate limiting "is per-instance, so N replicas multiply the effective limit by N — a shared store is the fix and needs a decision about which store." `deploy/kubernetes.yaml` already runs `replicas: 2`, so the defect is live in the one deployment manifest this repo ships.
- **Risks**: If the decision lands on Redis rather than MySQL, that is a new external service dependency in production — exactly the category `architecture.md`'s packaging model has avoided everywhere else (`docker-compose.yml`'s `full` profile already lists only mysql/nats/backend/projector/otel-collector, no cache layer). Building this before the store decision risks a rework.
- **Enablement**: Closes a real security-review-flagged gap (per the Security advisor's source review) without expanding infra footprint if MySQL is chosen — but that choice should be made explicit before implementation starts, ideally informed by Candidate 2's concurrency measurement.

#### 15. Signed Release Binaries

- **Score**: 2
- **Rationale**: The release pipeline itself is complete and gap-free (`release.yml` cross-compiles three platforms, uploads via `actions/upload-artifact`, and `apps/cli/.goreleaser.yml` already runs a full GoReleaser release) — but signing requires certificate procurement and signing-key custody that do not exist in this repository today, which is a genuine new infrastructure/secrets-management requirement, not a code gap.
- **Evidence**: Verified directly — `apps/cli/.goreleaser.yml` and `.github/workflows/release.yml` contain no `signs:`/cosign/sigstore configuration and reference only `secrets.GITHUB_TOKEN`; no Apple Developer, code-signing certificate, or HSM/KMS secret exists in the workflow. GoReleaser's native `signs:` block is real and would slot into the existing `apps/cli/.goreleaser.yml` mechanically — the gap is entirely external-credential custody, matching M12's own checklist note that this was "scoped out."
- **Risks**: Cosign's keyless flow depends on an external OIDC-to-Fulcio transparency-log service (sigstore's public infrastructure) — the first genuinely new *external* service this release pipeline would depend on, a step change from today's fully self-contained release job.
- **Enablement**: Closes a supply-chain integrity gap but unblocks no other roadmap item; it is a terminal hardening task, not a dependency for anything else in this list.

#### 16. CQRS with a Separate Read Store

- **Score**: 1
- **Rationale**: This is the one candidate that plainly breaks the packaging model this domain protects — a materialized read store means a new external service (OpenSearch or equivalent), confirmed not installed, plus a dual-write/consistency mechanism across all 19 backend modules that today share one transactional path.
- **Evidence**: `architecture.md`: "reads and writes both hit the transactional database... OpenSearch is not installed and nothing commits to it." ADR-0003 explicitly defers this decision pending the concurrency measurement that Candidate 2 does not yet provide. `tech-stack.md`'s Planned table lists no owner.
- **Risks**: Building this now means guessing at a store choice and a synchronization mechanism before the measurement that's supposed to justify it exists — the exact anti-pattern ADR-0003 was written to prevent, and every advisor who raised it in Round 1 scored it 1 for that reason.
- **Enablement**: None until Candidate 2 lands and produces the concurrency evidence ADR-0003 names as its own trigger condition.
